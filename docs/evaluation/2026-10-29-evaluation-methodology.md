# agent 调优的评价量化方法（2026-10-29）

## 一、当前方法的问题（用自己数据证明）

| 缺陷 | 实证 |
|---|---|
| **二元 0/1 掩盖进展** | 7 个 reward=0 的 trial 里有 3 个 partial≥75%：qutebrowser 104/105=**99%**、element 4/5=80%、tutao 3/4=75%。0/1 把它们当"完全失败"，无法区分"差 1 个测试"和"什么都没做" |
| **单次方差极大** | 同题一过一败（navidrome 基线 FAIL/FAIL/PASS）；同配置 token 917k–3.71M |
| **只看结果不看过程** | 无法诊断"为什么失败"（改测试？空转？探索发散？）|
| **成本高、不能高频** | 每题 20+ 分钟、100 轮，改一次跑一次不现实 |

## 二、更好的指标体系：三层

### A. 结果层（比 pass@1 更细，0 额外成本）
| 指标 | 定义 | 价值 |
|---|---|---|
| **partial credit** | 通过必需测试数 / 必需测试数 | 已验证可算；区分"差 1 个"与"全错" |
| **pass@k** | k 次采样至少 1 次成功 | 衡量能力上限，抗单次噪声 |
| **pass^k（一致率）** | k 次全部成功 | **衡量可靠性**——直击我们的方差问题 |
| 修复率 | 首次失败后最终成功的比例 | 衡量自纠错能力 |
| 回归破坏率 | PASS_TO_PASS 被破坏比例 | 衡量"没改坏" |

### B. 过程层（免费，从轨迹 events 直接算）
| 指标 | 说明 |
|---|---|
| 步数 / 工具调用数 | 效率 |
| 重复读同一文件率 | 探索冗余（实测 keyutils.py 被读 59 次）|
| 改既有测试次数 | 机制保护触发次数（restored-test-files.json）|
| 空转率 | patch=0 或 token 爆炸（tutao 就出现过 patch=0）|
| 首次编辑前的探索步数 | 规划质量 |
| 模型 API 失败次数 | 环境健康 |

### C. 效率层
- token / 时间 / credits **per 成功任务**（而不是 per 调用）

## 三、评测设计的统计方法（更少样本得出更可信结论）

1. **配对设计 + McNemar 检验**：同题跑 A/B，用配对显著性检验——比独立样本省 30–50% 题量。
2. **方差分解**：把总方差拆成"题间"与"题内"。题内方差大（如我们）→ 同一题要多重复；题间方差大 → 要多题目。
3. **分层抽样 + 分层报告**：按仓库/难度分层，分别报告（HARD-51 与整体是不同分布）。
4. **报告置信区间**（Wilson/bootstrap），不报单点。
5. **报告效应量**（risk difference / Cohen's h），不只看"过没过"。

## 四、低成本高频的评价体系（个人开发者友好）

**三层金字塔**：
| 层 | 规模 | 反馈时间 | 成本 | 用途 |
|---|---|---|---|---|
| **L1 单元/诊断场景** | 若干小场景 | 秒级 | ~0 | 特定能力切片（工具选择、上下文、协作），改提示词先在这测 |
| **L2 快速回归集** | 5–10 道代表题 | 分钟级 | 低 | 每次改动的冒烟测试 |
| **L3 正式评测** | 60–120 题 ×2–3 重复 | 小时级 | 中 | 里程碑验证 + 统计结论 |

**护栏机制**：L1/L2 的过程指标不达标（改测试次数↑、空转率↑、步数↑），先不跑 L3。

## 五、针对已发现问题的具体映射

| 我们遇到的 | 应改用的指标 |
|---|---|
| 同题一过一败 | **pass^3 / 一致率**（而非单次 pass@1）|
| FAIL 但过了 4/5 测试 | **partial credit** |
| 改既有测试 / 空转 / 探索发散 | **过程指标**（零成本）|
| 样本小 CI 宽 | **配对 McNemar** + 分层 |

## 六、立即可做（0 额外成本）

用现有数据即可算出上述大多数指标：
- partial credit：验证器输出已有 `Required tests / Passed tests`（已验证可提取）
- 过程指标：`events.jsonl` 已有工具调用、token、时间线
- pass@k / 一致率：现有重复数据可重算

**建议**：做一个统一的"评测分析器"，把每个 job 目录扫一遍，输出：partial credit、步数、重复读、改测试次数、空转标记、pass^k、CI。这样即使只跑 3–5 题，也能从**过程+部分得分**里读出方向，而不是只看 0/1。

## 七、结论

**从"端到端 pass@1"转向"partial credit + pass^k + 过程指标 + 配对统计"**：
- 信息量提升一个量级（0/1 → 连续分数 + 过程诊断）
- 成本大幅下降（L1/L2 秒级~分钟级，不用每题跑 100 轮）
- 统计更可信（配对 + 重复 + CI）

## 八、指标 vs 题量：准确的关系（别搞成二选一）

**两者是"乘法"不是"加法"，解决不同问题：**

| | 题量 | 指标体系 |
|---|---|---|
| 解决什么 | **代表性 / 外部效度**（结论能否推广）| **信息效率 / 诊断力**（同一批数据榨出多少信息）|
| 成本性质 | **付费杠杆**（更多时间/token/钱）| **免费杠杆**（同一批数据重算即可）|
| 硬上限 | 可评测 519 题；预算内 120–180 | 无上限 |
| 能不能互相替代 | **不能** | **不能**（指标不解决题目异质性导致的 CI 宽）|

**所以准确的说法是：**
1. **高频迭代阶段**（每次改代码）：**指标为主**——3–5 题回归 + 过程指标，分钟级反馈，成本几乎为 0。
2. **里程碑验证**：**题量 + 重复 + 指标**——120–180 题 ×2，partial/pass^k 一起报。
3. **对外结论**：题量（和重复）**不可少**，指标无法替代统计样本量；要检测 10pp 以下效应，只能靠题量/重复。

一句话：**指标让每道题更有信息，题量让结论更可信；指标不能替代样本量，样本量也给不了指标那样的诊断力。**

## 九、必须警惕：指标本身可被"刷"（Goodhart 陷阱）

指标体系如果不抗刷，会制造新的自欺：

| 指标 | 怎么被刷 | 抗刷手段 |
|---|---|---|
| partial credit | **改测试**让必需测试通过 → partial 虚高 | 同时报"改既有测试次数""回归破坏率" |
| pass@k | 多次采样取最优 → 掩盖稳定性问题 | 同时报 **pass^k（一致率）** |
| 步数下降 | 跳过必要探索 → 看似高效实则漏改 | 配合 partial credit 与空转率 |

我们已踩过的坑：`partial credit` 完全可以靠"改测试"刷高（正是 5/5 失败的根因）。**所以任何结果指标都必须配过程护栏**（改测试次数、空转、回归破坏率），否则会优化出"看起来更好、实际更差"的版本。

这也是为什么"机制保护（禁止改测试）+ 过程指标"是配套的，而不是可选。
