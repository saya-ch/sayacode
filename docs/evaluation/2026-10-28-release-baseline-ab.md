# 正式发布版 vs 优化候选：配对评测（2026-10-28）

## 基线定义

- **基线 = 正式发布版 v3.2.4**，Git tag `v3.2.4` → commit `2afe5889`，用 `git archive` 导出干净源码后构建 wheel（507,960 字节）。
- **候选 = 当前工作树**（含提示词兼容规则、批量调用规则、多 Agent 派发触发规则、审计缓存字段、评测缓存统计），构建 wheel（514,093 字节）。
- 两个 wheel 均确认：发布版不含 `Dispatch trigger` 与兼容性规则，候选版含。

## 实验条件

- 数据：官方 SWE-bench Pro V2 dev 任务（qutebrowser、openlibrary、ansible、NodeBB）。
- 模型：本机 Magpie `auto/deepseek-v4.1-flash`（Anthropic 协议），同一天同一网关。
- 判分：官方 Harbor 验证器，`reward` 为唯一成功判据。
- 设计：同题、同重复编号配对，2 并发。

| 总时长 | 1,821s | 2,551s | +40.1% |

## 结论（必须照实说）

1. **在这个配对样本上，优化候选没有任何正确性收益，token 与时长反而更差。**
2. 此前单次观察到的「qutebrowser 由 0 变 1」**未能复现**：同一套规则下，历史上 qutebrowser 结果为 PASS、FAIL、PASS、FAIL（2/4）；发布版为 FAIL、FAIL（0/2）。差异方向对候选有利，但样本量与方差都不足以支持"修复有效"的结论。
3. 根因未被真正消除：qutebrowser 的失败是「删掉既有 `to_int` 接口 + 改写既有测试」，提示词规则降低了概率，但没有稳定阻止。
4. **NodeBB 未计入**：其官方验证器（NodeBB 全量 JS 测试套件）在本机单次超过 1 小时仍未结束，已终止以避免阻塞；这是本地评测的可用性限制，不是产品结论。
5. 因此本轮**不能宣称优化有效**。任何"提升"的说法都需要每格 ≥5 次重复的配对数据。

## 教训与方法论

- 单次/两次运行的结果会给出错误印象：同一 wheel 下 qutebrowser、vuls 都出现一次通过一次失败。
- 以正式发布版为基线做配对，立刻纠正了此前中间态对比造成的乐观偏差。
- 真正的成本杠杆不在提示词长度（系统提示仅约 500–700 tokens/次），而在会话增长：单题输入达 70 万–1,600 万 tokens。下一步应优先实验上下文管理（更早摘要、清理旧工具结果），并用同样严格的配对流程度量。
