# SAYACODE 首轮 Agent 评估记录

日期：2026-10-21。本文记录已执行的工作、评分合同更正和未完成的研究问题。数字来自独立结果目录，不是示例成绩。

## 结论范围

已经建立固定任务、外部行为验收、真实产品执行、原生审计、配对重复和报告链路。完整执行了 144 次主批次试验。

本轮数据**不能证明多 Agent 提升质量或速度**：两个组都没有实际派发子任务，且出现了集中连接失败。摘要专题受到配额限制，没有形成有效对照。此处保留这些负结果，不以正常结束的子集替代整体成功率。

## 数据与评分合同

默认任务集共 8 道开发题、24 道验收题，分属 13 个小型 Python 仓库家族。全部为人工构造，未使用企业私有数据，也没有将它们称为真实用户失败样本。

验收题包括：8 道缺陷修复、6 道跨模块功能、4 道理解／审查、6 道确定性多轮需求更新。20 道编程题采用隐藏 Python 行为检查、原有公开回归和明确受保护文件检查；4 道审查题仅进行自动预筛，仍需人工判分。

开发与验收按仓库家族分开。同一家族内任务仍有关联，不能把重复试验视为独立项目。短多轮任务不等于长上下文摘要评估。

### 初版判分错误与更正

v0.1 未在题面公开 README 和原测试文件的字节保护条件，模型补充文档或测试后，即使功能检查通过也被判失败。这是评估设计错误，不能描述成 Agent 修复失败。

发现后中止该批，保留 27 条完成记录、4 条中断现场和旧数据合同。没有修改旧分数或从中挑选成功记录。

v0.2 对所有题目统一明示受保护路径，允许在其他文件补测试；隐藏功能规则、原 fixture 和验收标准没有降低。随后重新运行完整批次。两个数据版本的分数不能直接比较，也不能将这一合同澄清说成模型或 Agent 提升；沿用的题目不再是全新未见的盲测。

## 主批次：144 次真实试验

两组使用相同任务、模型、基础工具、规划和上下文策略：

- `single`：实际工具 schema 不注册团队工具。
- `team`：注册团队工具，是否派发由模型自主决定。

每组 24 题，每题独立重复 3 次。先区分运行结束，再验收产物；不以 Agent 自称完成或退出正常作为成功依据。

### 失败归因与比较边界

原生审计支持以下终态分类：

- 77 次代码验收通过。
- 11 次正常完成、待人工审查。
- 53 次最终模型连接类失败。
- 3 次超过实验时间预算。

连接失败集中于部分时间段。现有记录不能将具体故障完整定位到容器网络、反代或上游；不能笼统归因于“模型不会做题”。后续诊断试验捕获了 `RemoteProtocolError` 类型链，仍不足以锁定单一根因。

两个组实际创建的子任务均为零。因此，本轮衡量的是**团队工具可用性的初步对照**，没有衡量到真实异步协作的净收益。组间比例差异也受到服务波动影响，不能作机制因果结论。

## 摘要专题与配额中断

专题另有两道开发场景：先给 API 约束，再发送三段固定合成日志，最后要求实施；最终函数行为由外部检查验收，不与主批次混算。

4,096-token 开发压力试验在 600 秒预算内未完成。读取原生检查点历史，观察到 15 个不同摘要版本、139 个检查点；同时出现 HTTP 协议错误。不能把超时完全归因于摘要，也不能由它推翻生产默认的 80% 阈值。

该低阈值低于已观察到的一次初始请求输入量，因此后续开发对照选择 16,384-token 触发、保留 2 条近期消息，与关闭摘要比较。这是根据开发试验选择配置，不是最优阈值证明。

后续 12 次尝试遭遇 10 次明确的 `429 RATE_LIMITED` 和 2 次连接失败。服务返回五小时额度耗尽；该批原始数据保留并标记为不可用于摘要机制比较，**没有有效摘要收益结论**。

显式要求 planner／reviewer 协作的独立场景已准备，但因同一配额限制没有调用真实模型。不得将场景定义或单元测试冒充已完成的真实协作评估。

## 由评估反馈的工程修改

已完成：

1. 在唯一应用组装处提供团队工具开关，避免仅靠提示词禁止派发。
2. 固定任务与源码身份、独立状态与容器、外部判分、原始结果及未知用量。
3. 分开自动编码、待人工审查、运行错误、重复稳定性和实际派发数。
4. 失败审计增加有界异常类型链与状态码，不记录错误正文、请求、响应或凭据。
5. 在实验运行器增加任务族各线程终态 401／403／429 停止后续派发，以及中止／失效报告标记；清理失败仍保存中止原因。

本地模拟 HTTP 429 的真实框架链路故障注入中，计划的两道任务只生成一个实际试验记录，第二道未派发，中止原因为 `model_rate_limit`，没有付费模型调用。

该注入还观察到：关闭模型中间件重试后，一次回调层模型调用仍对应三次 SDK HTTP 尝试。因此当前回调计数不代表完整请求账本；本轮没有修改 SDK 或反代重试策略，也没有宣称解决了重复请求计费。

以上是可追溯性、合同和失效控制的改进，不是已经证明的 Agent 解题能力提升。主批次候选身份如前；随后新增的诊断与停止控制只完成相应离线或模拟验证，未在真实配额恢复后补充实测。

## 继续工作的顺序

1. 接口额度恢复后，用新结果目录补跑摘要专题和一次显式协作诊断；保留受限批次，不能补挑成功样本覆盖。
2. 对 4 类审查任务建立人工标注，先校准评分，再评价审查能力。
3. 扩大可并行的真实任务，加入真实历史 issue／跨模块工作；先解决“没有实际派发”这个测量缺口。
4. 针对网络和重试增加受控故障场景，明确框架调用、SDK 请求和反代尝试的观测边界。
5. 形成足够稳定的基线后，再对规划、工具选择、记忆、Skill 做单因素消融，补充独立新任务验收。
