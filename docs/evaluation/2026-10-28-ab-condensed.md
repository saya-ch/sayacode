# 提示词精简 A/B 实验记录（2026-10-28）

## 研究问题

把系统提示词压缩 30% 能否在**不降低成功率**的前提下减少输入 token 与总时长？

## 实验设计

- 数据：官方 SWE-bench Pro V2 dev 任务中的 4 道（qutebrowser、openlibrary、ansible、NodeBB），覆盖 Python / JavaScript 与大 / 小 token 画像。
- 每题 × 2 重复 × 2 个 wheel，共 16 次试验，2 并发。
- 同一模型（Magpie `auto/deepseek-v4.1-flash`，Anthropic 协议）、同一官方验证器、同一隔离网关。
- 唯一变量：产品 wheel 内嵌的系统提示词。

| 版本 | 系统提示 | 说明 |
|---|---|---|
| A 优化版 | 2,696 字符 | 含「新增接口与旧接口并存」「不得改写既有测试」等完整规则 |
| B 精简版 | 1,894 字符 | 同样保留关键兼容约束，其余措辞压缩（−30%），少 1 条规则 |

两版均通过同一回归测试（断言关键兼容约束存在）。

## 结果

| 版本 | 成功率 | 总输入 token | 总时长 | 中位输入 | 最大输入 |
|---|---:|---:|---:|---:|---:|
| A 优化版 | **6/7（86%）** | **13,703,704** | **3,433s** | 1,366,654 | 6,350,145 |
| B 精简版 | 6/8（75%） | 25,456,609 | 5,316s | 1,714,382 | 16,008,247 |

A 的 NodeBB r2 为基础设施错误（29 秒即中断，无 token/评分），不计入成功率分母但如实保留。

B 的 qutebrowser r2 撞满 49 分钟任务预算，**单次烧掉 16,008,247 输入 token**，是 B 总量膨胀的主因。

## 结论

**精简提示词三项目标全部落空：**

1. 成功率更低（75% vs 86%，n 小但方向不利）；
2. 总输入 token 反而增加 86%；
3. 总时长增加 55%。

原因分析：系统提示只占每次调用约 500 tokens，而真实成本由**会话增长**（工具输出、回合数）主导，两者相差一个数量级以上。压缩规则措辞省下的约 200 tokens/调用，远抵不上「少了一条有效引导」导致的额外探索回合。B 版 qutebrowser r2 的超长探索正是证据。

**决策：保留 A 版（优化版）提示词，不采用精简版。**

## 方法论警示

本轮再次证实单次运行方差巨大：

- openlibrary 同一任务同一模型：203k / 445k / 410k / 6.35M / 1.65M token 不等，相差 30 倍；
- wheel-A 的 qutebrowser 一次失败一次通过；
- wheel-B 的 openlibrary 一次失败一次通过。

**在 n=2 的条件下，任何版本间的 token 或成功率差异都被随机性淹没。** 要宣称某个提示词改动能稳定降低成本，需要 ≥5 次重复并按任务块配对；对成功率则需要更大的题量。
