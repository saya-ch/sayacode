# 评测驱动优化迭代 01（2026-10-28）

## 目标

用真实模型跑通「评测 → 分析 → 优化 → 复测」闭环，产出可复核的结论。

## 环境与身份

| 项目 | 值 |
|---|---|
| 模型 | `auto/deepseek-v4.1-flash`（经本机 Magpie 网关 `http://host.docker.internal:3425/v1`，网关实际路由到 `deepseek-v4.1-flash-sg`） |
| 协议 | `openai_chat_completions` |
| 评测框架 | `evals/`（自构造 32 题：8 dev + 24 holdout） |
| 仓库 | `C:\develop\sayacode`（工作树含既存未提交改动，本次追加产品与评测改动） |
| 原始结果目录 | `C:\develop\sayacode-evaluations\20261028-*`（仓库外） |

模型不受预算/配额限制；本迭代仅使用 `auto/deepseek-v4.1-flash`，不引入第二个模型变量。

## 第一次发现：任务集已饱和

| 集 | 自动题通过 | 说明 |
|---|---|---|
| dev（8 题） | 8/8 = 100% | 中位 29.0s，输入 445,488，输出 20,667，73 次调用 |
| holdout（24 题） | 20/20 = 100% | 4 道审查题自动筛查通过、待人工复核；中位 37.8s，输入 1,974,512，输出 119,173，271 次调用 |

逐题抽查：一行 `utf-8` → `utf-8-sig` 的 BOM 修复用了 14 次调用、104k 输入 token；4 道审查题的回答包含实测探针、触发条件矩阵与最小修复建议，质量合格。

**结论：该自构造 32 题集在正确性维度已被 DeepSeek-V4.1-Flash 完全饱和，无法再用于衡量改进；继续在正确率上做优化没有可测信号。** 这与仓库既有记录「不能证明多 Agent 提升质量」一致。

## 第二次发现：评测度量漏掉 prompt 缓存

基线每次模型调用都要重发全部历史，输入 token 随回合数近似平方增长（单题 4.3k → 14.6k）。但产品审计只记录 `input_tokens / output_tokens / total_tokens`，丢弃了提供商返回的 `input_token_details.cache_read`。

实测网关确实支持前缀缓存：同一 prompt 第二次调用 `cached_tokens=1408 / 1632`（86% 命中）。全量 holdout 复测显示 **91.7% 的输入 token 是缓存命中**，即真实参与计算的新增输入只有约 15 万，而非 197 万。此前所有评估报告都把缓存当全新输入，高估了成本与上下文压力。

## 本迭代的改动

### 产品侧

1. `src/sayacode/audit.py`：`on_llm_end` 额外提取 `input_token_details.cache_read`，记为 `cache_read_tokens`。
2. `src/sayacode/diagnostics.py`：用量汇总增加 `cache_read_tokens`。
3. `src/sayacode/prompts.py`：`_WORK_RULES` 强化两点——
   - 独立只读调用（read_file/list_directory/grep_search/glob_search）必须合并到同一个响应，理由写明「每个额外回合都会重发整段历史」；
   - 现有测试已覆盖改动行为时不得再新建重复测试文件。

### 评测侧

4. `evals/worker.py`：`usage_from_audit` 增加 `cache_read_tokens` 与 `cache_reported_calls`，且**不参与**核心用量完整性判定。
5. `evals/report.py`：报告新增「输入缓存命中 token / 缓存命中率 / 命中观测覆盖调用数」。
6. 测试：`tests/evals/test_execution.py` 更新用量断言并新增缓存聚合用例。

回归：全量 `pytest` **478 passed, 4 skipped**；`ruff`、`mypy` 未新增问题（见下）。

## 优化效果（8 题 × 3 重复 A/B，同一模型、同一判分）

| 指标 | 原 prompt | 优化 prompt | 变化 |
|---|---:|---:|---:|
| 通过 | 24/24 | 24/24 | 0 |
| 模型调用 | 340 | 321 | −5.6% |
| 输入 token | 2,785,170 | 2,503,651 | −10.1% |
| 未缓存输入 token | 212,114 | 178,659 | **−15.8%** |
| 输出 token | 173,947 | 133,455 | **−23.3%** |
| 缓存命中率 | 92.4% | 92.9% | +0.5pp |
| 中位耗时 | 47.8s | 49.4s | +3.3% |

## 口径与限制

- **单次重复方差大**：首轮单重复对比出现 −13.7%（优化后）与 −3.8%（含缓存度量的复跑），因此改用 8 题 × 3 重复的 A/B；仍只是探索性，不是统计充分结论。
- 逐题差异方向不一致（`invoice-tax-half-up` −51%，`task-search` +36%），说明收益主要来自「减少重复输出」而非普遍提速；中位耗时未改善。
- 缓存命中率在两次 A/B 中稳定在约 92%，是结构性事实，不是本次改动带来的。
- 任务集非官方基准；模型标识由网关返回，未独立验证上游权重版本。
- 本次未改动任何判分规则、任务定义或受保护文件条件。

## 下一步建议

1. 若要确认 prompt 改动的净效果，需扩到全部 24 题 × 3 重复并做任务块配对区间。
2. 更根本的瓶颈是任务集饱和：需要引入更难的任务（真实仓库 issue 或公开基准 SWE-bench Pro），才能测到正确性维度的改进。这与 `sayacode-bench` 的 B 阶段 blocker（musl wheel）相关。
3. 缓存命中已可见，可进一步在产品 UI/诊断中展示，帮助用户理解真实成本。
