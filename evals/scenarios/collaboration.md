# 显式协作诊断场景

`collaboration.jsonl` 只有 1 道 `split=dev`、`category=collaboration_diagnostic` 任务，复用 `holdout-parcels` fixture，把既有查询、幂等登记与取消能力组合在同一次运行中。

**这是用户明确要求协作时的功能诊断，不是比较 Agent 是否自主派发的无偏 benchmark。** 它组合了已经使用的三道任务，既不是新的独立样本，也不计入原有 24 题验收分数。默认数据集 v0.2、fixture 与上下文摘要专题均保持不变。

## 明确分工

题面要求：

1. 派发一个只读 planner 调查存储层的查询、find 与幂等接口。
2. 派发一个只读 reviewer 调查服务层状态变化与集成风险。
3. 子任务运行时，主 Agent 独立阅读领域模型与公开测试，调查取消行为和回归要求。
4. 收齐两份报告后，由主 Agent 实施全部功能并综合验证。

子 Agent 负责调查与报告，主 Agent 负责写入。题面明示不得改动或删除 `README.md`、`tests/test_public.py` 的任何字节；补充测试应新建文件。

## 判分与观察

复用原有三题的完整功能要求与原样隐藏行为检查，公开 unittest 去重后仅运行一次。共有 4 项文件/行为检查：

- 1 项公开 unittest。
- 3 段外部 Python 隐藏行为断言，分别覆盖查询、幂等与取消。
- 另由运行器检查受保护文件完整性。

场景同时声明：

- `min_child_tasks=2`。
- `max_failed_child_tasks=0`。
- 整题超时预算 600 秒。

运行器应依据实际持久化子任务与终态计数，不能依据主 Agent 的回复自述判断是否协作。还应保留父子调用关系、任务状态、报告与主 Agent 后续工具轨迹。

仅有子任务数量不等于证明所有协作要求：是否在子任务运行期间独立调查、是否收齐报告后再实施、是否实际使用报告中的结论，应结合事件时间线与报告进行复核。若没有自动顺序断言，应在结果中明确这部分属于轨迹复核，不能将其误写成全部自动验收。

## 运行与结论边界

只运行协作配置一次，用于检查显式派发链路、子任务完成与综合交付。单次成功至多说明本场景在该配置下实际运行成功，**不支持多 Agent 比单 Agent 更优、更快或更省 token 的结论**。

原有三段隐藏判分已做初始缺陷负例与临时参考实现正例检查；本文件没有改变功能评分、保护路径或原 fixture。只对合并后的 JSON 和判分代码做结构/语法检查，不把它当成新的模型运行成绩。

如需研究协作收益，应另做固定配置、任务配对、重复试验和完整成本统计；本诊断的“用户要求派发”设置不能替代自主派发策略评估。
