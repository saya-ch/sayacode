# 上下文摘要专题 v0.1

## 定位

`context.jsonl` 是独立于 `evals/cases/` 的开发场景清单。共有 2 道 `split=dev`、`category=context_summary` 的人工构造题，分别引用原有 `dev-notes` 与 `dev-metrics` fixture。**没有修改冻结的 32 题、原 fixture 或 freeze.json，也不将本专题混入 24 题验收总分。**

本专题只评估：经过一段固定背景材料并执行摘要后，Agent 是否保留了开头的可验证 API 与行为约束。它不是实际用户失败样本，也不是大型仓库完整开发任务。

## 固定轮次

每道题包含 5 轮用户输入：

1. 开头给出完整 API 和行为契约，要求只确认，不读写文件、不提前实现。
2. 一段普通合成构建日志，只确认，不产生新需求。
3. 第二段普通日志，规则不变。
4. 第三段普通日志，规则不变。
5. 要求按对话开头约定实施并验证，不重复关键约束。

每段日志为 **26,546 个 UTF-8 字节**，没有真实项目数据、网络地址、凭据、权限请求或附加开发指令。日志正文是确定性的普通编译进度材料。要求“只确认”的文本位于日志外，用来固定运行步骤。

本地用两种 tiktoken 编码统计完整用户输入：

| 场景 | cl100k_base | o200k_base |
|---|---:|---:|
| context-notes-export | 12,962 | 12,855 |
| context-metrics-window | 12,966 | 12,843 |

这些只是公开 tokenizer 的长度估算，**不是 DeepSeek 真实计费 token**，也没有包含系统提示、工具定义、模型回复或工具输出。实际输入用量应来自运行元数据。

日志刻意重复，具有高可压缩性；这会降低任务难度，不应将本结果推广到复杂源码、工具观察或相互矛盾的真实长上下文。

## 两道任务

### context-notes-export

新增 `notes.export_notes(path, notes)`，隐藏行为检查包括：

- UTF-8 JSON 数组与中文原文。
- 标题按 Unicode casefold 排序，相同键保持原顺序。
- 保留完整记录和嵌套字段。
- 不改变输入列表或记录。
- 创建多级目录，支持字符串及 Path。
- 返回导出条数，空列表正确导出。

### context-metrics-window

新增 `stats.window_mean(values, width)`，隐藏行为检查包括：

- 步长 1，只计算完整窗口。
- 正整数宽度，明确拒绝 bool、0、负数和非整数。
- 大于长度、等于长度、空序列等边界。
- 不修改输入。
- 不破坏公开的 mean/percentile 回归测试。

两个场景均为 `human_review=false`，最终代码通过外部 Python 断言、公开 unittest 和受保护文件完整性共同验收。没有使用 LLM 自评。

## 配对实验约定

使用同一模型、同一模型窗口、同一题面和 fixture，单 Agent 执行。除摘要条件外保持其余资源相同。

| 配置 | 关闭摘要组 | 专题摘要组 |
|---|---|---|
| 模型配置窗口 | 相同的 64K 配置 | 相同的 64K 配置 |
| 最大输出 | 8,192 token | 8,192 token |
| 摘要保留消息 | 无摘要 | keep=2 |
| 摘要触发阈值 | 关闭 | 16,384 token |
| 重复次数 | 每题 3 次 | 每题 3 次 |

合计 2 题 × 2 配置 × 3 次 = 12 次完整试验，每次包含上述全部轮次。清单中的 `timeout_seconds=600` 是整道多轮任务的实验预算，不应每轮重新获得完整预算。

开发压力试验曾使用 4,096 token 阈值；该试验在 600 秒预算内未完成，原生检查点中观察到 15 个摘要版本，同时有 HTTP 协议层错误。原始记录单独保留，不能把超时完全归因于摘要，也不能用它证明生产默认策略失效。该阈值还低于已观察到的一次初始请求输入量，因此正式开发对照改用 16,384；这是开发场景调试后的配置选择，不是无偏的最优阈值结论。`summary-pressure-4096.json` 保留原压力配置。

2026-10-21 的后续对照遭遇接口五小时配额耗尽，未形成有效摘要收益比较。已经执行过的失败和配额记录保留，不能改成成功或和编码批次混算；原始条件与参数见对应实验 manifest。

不要只根据输入长度或配置推断摘要已经执行。每次试验都需要从真实图状态、摘要消息或明确的中间件观测记录提取 **summary_count**。只有 `summary_count > 0` 才能称为“已触发摘要”；未触发时应单独标记，而非并入摘要效果结论。两组均需保留原始用量和最终行为判分。

任务第一轮要求不提前实现。若 Agent 提前写入文件，应记录为协议违反；即使最终代码通过，也不能将该次试验解释为纯粹的“摘要后才实施”成功。执行器若没有逐轮差异检查，必须明确这项观察缺口。

## 自检与局限

在无模型条件下，已验证：

- 两个初始 fixture 的新增函数缺失，隐藏判分均以非零退出失败。
- 临时目录中实施参考实现后，两题的隐藏检查与公开回归均通过。
- 参考实现没有写入 fixture 或仓库。

这些自检不等于真实模型实验结果。

需要与成绩同时声明：

- 只有两个合成场景，统计能力很弱；可报告逐次计数，不宜声称普适提升。
- 开头契约短、背景材料重复，因此比真实长仓库轨迹简单。
- 只检查最终行为，不覆盖摘要的所有事实或每条中间推理。
- 低阈值摘要是一项专题实验，不代表生产默认阈值。
- 独立评分目录仍不是安全沙箱；全局 Shell 可以读取宿主路径时，不能宣称隐藏材料绝对不可见。
- 两题复用已有 dev fixture，因此只能作为开发专题；不得伪装成新的独立 holdout 任务。
