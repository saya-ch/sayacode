# SAYACODE Agent 评估任务集 v0.2

## v0.1 中止与 v0.2 合同澄清

v0.1 将 README、公开测试等文件列为逐字节保护对象，但部分题面没有向 Agent 公开这些路径和保护要求。模型正常补充或修改公开测试后，仍可能因未告知的文件保护条件判失败。这是评估合同缺口，不能直接归因于模型任务能力。

发现后已中止 v0.1 批次，保留 27 条已完成及 4 条中断原始记录，并备份完整 v0.1 数据集；中断记录不伪装为完成结果。本轮修订将版本提升为 v0.2：

- 仅在全部 dev/holdout 首轮题面追加既有受保护路径，明确禁止修改、删除和任何字节改变；需要补充验证时应新建其他测试文件。
- 隐藏功能判分、保护路径、通过条件和 fixture 内容均不改变，没有降低验收标准。
- 这是将原本未公开的评分合同明确告知，不是模型能力、Agent 实现或提示优化带来的改进。
- v0.1 与 v0.2 的分数不能直接比较，也不能把题面澄清后的差异包装为系统效果提升。

数据字段继续使用 split=holdout 表示原有家族拆分，但这些任务已有运行记录与结果被查看，**不能再宣称是全新未见 holdout**。v0.2 应称为“已使用任务上的冻结对照验收集”；新一轮泛化结论需要另外建立真正未使用的任务家族。开发与验收家族仍保持原有隔离。

## 来源与适用范围

本任务集包含 **8 道开发题、24 道冻结验收题，13 个独立 fixture 家族**。全部为人工构造的 Python 标准库小仓库，**不是从真实用户日志或历史 issue 收集的失败案例**，也没有声称代表真实企业任务分布。

目的：先验证评估链路可复现、判分确有区分能力，并对固定模型下的单 Agent 与多 Agent 运行做初步配对比较。任务规模小，通常不需要多 Agent；是否派发、派发是否增加协调成本，本身也是结果。不能根据这套小任务集宣布行业领先、达到 SWE-bench 水平或证明大仓库能力。

冻结意味着运行前确定题面、fixture、followup 和评分器，不在看到验收成绩后只针对某道题修改规则。若发现规则错误，应提升数据集版本，保留旧结果和更正原因，重新评估相关配置。

## 拆分与数量

| split | 家族 | 任务数量 | 用途 |
|---|---|---:|---|
| dev | dev-inventory、dev-notes、dev-metrics、dev-workflow | 8 | 调试运行器、评分器、提示和结果格式 |
| holdout | holdout-invoice、holdout-log-window、holdout-csv-importer | 8 | 缺陷修复 |
| holdout | holdout-parcels、holdout-task-board | 6 | 跨模块功能与集成 |
| holdout | holdout-order-flow、holdout-config-load | 4 | 仓库理解、代码审查 |
| holdout | holdout-note-exporter、holdout-report-pipeline | 6 | 多轮需求变化、动态修正 |

开发集与验收集按 **整个 fixture 家族** 隔离。两份 split 没有复用同一 fixture、没有通过换函数名跨 split 制造近重复。同一家族内部的任务共享初始仓库，执行时必须每题独立复制，不能将前题的修改累积到后题。统计时应注意同家族任务相关，不能把 24 题视为 24 个完全独立的项目。

## 数据格式

- `dev.jsonl`、`holdout.jsonl`：每行一个完整任务。
- `id`：稳定标识。
- `split`：`dev` 或 `holdout`。
- `category`：`bugfix`、`feature`、`multi_turn`、`repository_understanding` 或 `code_review`。
- `fixture`：相对于 `evals/fixtures/` 的目录。
- `prompt`：首轮确定性用户任务。
- `followups`：首轮运行完成后，依次作为新用户轮次发送的固定文本。
- `checks`：外部评估宿主执行的判分规则，不复制到 Agent 工作目录。
- `protected_paths`：要求保持内容和存在性不变的相对路径。
- `tags`：来源、并行适用性、需求反转等标签。标签不是观测结论。
- `timeout_seconds`：单题实验预算，默认 300 秒；多轮题预算应覆盖全部轮次。
- `human_review`、`human_rubric`：是否必须人工复核及其判据。
- `source`：明确任务是人工构造。

`python` 类型的 `code` 应由外部评分进程以 fixture 副本作为 cwd 运行；非零退出表示失败。`command` 使用当前 Python 运行公开 unittest。其他规则检查最终响应的字面证据；关键词仅作预筛，不是语义正确性判分。

## 独立判分

### 20 道验收编程题

每题同时满足以下条件才通过：

1. 全部外部隐藏行为检查通过。
2. 全部公开回归测试通过。
3. 受保护路径未被修改或删除。
4. Agent 运行没有失败、超时或未处理审批暂停。

隐藏检查覆盖输入边界、对象/文件副作用、跨模块 API、CLI 子进程和最终用户需求。题目没有要求固定编辑步骤或工具序列；只要合法完成行为即可。特意保留初始代码中与本题无关的其他问题，Agent 不应为了“顺手清理”破坏既有行为。

### 4 道理解/审查题

这些任务全部有 `human_review=true`。关键词只检测回答是否包含基本代码证据，**关键词通过不能自动记为任务成功**。

人工复核需要逐项读取 `human_rubric`、源码与响应，判断：

- 结论是否正确且有文件/符号依据。
- 是否给出真实可发生的反例或时序。
- 是否区分已知源码事实、题面假设和未知外部实现。
- 是否出现无依据的风险、虚构组件或伪造验证。
- 是否遵守只读要求。

未完成人工复核的结果标为待人工，不能混入编程题的自动成功率。报告分别展示自动可判任务和人工任务，不制造 24 题统一总分。

## 多轮执行语义

8 个 dev 中 2 题、24 个 holdout 中 6 题有固定 followup：

1. 使用新线程，在干净 fixture 上发送 prompt。
2. 等待这一轮达到真实终态；若失败、超时或暂停，记录原因。
3. 依次发送 followups，每轮仍使用同一线程和工作目录。
4. 所有用户轮次结束后，对最终产物做隐藏与回归检查。

这些题检查需求更新、保留历史约束与动态修改能力。它们没有达到模型上下文窗口的摘要阈值，**不能据此宣称验证了长上下文压缩**。摘要专题需要独立数据集：固定足够长的可验证输入、真实触发摘要，并检查压缩前后的约束与结果。

这批多轮题也不验证运行中排队/直接插话；需要另外的生命周期故障测试，不将异步交互契约与任务效果合成一个指标。

## 初始判分自检

在没有调用模型的条件下完成了两类检查：

- **负例**：28 道编程题的初始公开回归全部通过，隐藏行为检查全部失败；证明当前缺陷或缺失能力确实能被检出。
- **正例**：在一次性临时目录逐题实现参考改动，28 道编程题全部通过公开与隐藏检查；参考实现未保存在 fixture 或仓库中。

以上检查证明评分规则对选定正负例有区分能力，**不证明规则完整、任务无歧义或真实模型成功率**。4 道人工题仍需要真实回答后人工判分。初始分布、数据集文件和 fixture 的 SHA256 见 `freeze.json`。

## 实验与报告口径

- 首先只在 dev 上检查真实模型接入、耗时与预算；不要看到 holdout 成绩后继续调整同一轮实验。
- 单 Agent 与协作组使用相同模型、任务、基础工具、上下文策略与预算；协作组只改变团队工具可用性。
- 以任务为配对单位，重复三次时同时报告单次成功比例与三次全部成功的题数。
- 计入失败/超时消耗，包含父子 Agent、摘要和辅助模型调用；缺失 token 元数据明确标未知。
- 这批任务偏小，应报告逐家族结果与原始计数；不对小样本 P95 或微小均值差异做强结论。
- 至少保留任务 ID、模型配置（脱敏）、代码版本、数据集哈希、运行预算、产物差异、判分结果与失败轨迹。
- 不使用 Agent 自称“已经完成”或退出码 0 替代行为验收。
- 不使用 LLM 对自己的结果进行循环自评；后续采用 LLM judge 需另做人工校准、固定 rubric 并报告分歧。

## 环境与边界

fixtures 仅依赖 Python 3.11+ 标准库，无网络依赖。公开测试可运行：

```powershell
python -m unittest discover -s tests
```

只有 11 个家族带公开测试；两个只读审查家族主要通过人工与文件完整性判分。实际任务执行应只复制选定 fixture，不把整个仓库、其他题面和评分器同时放入 Agent 工作目录。

**分开目录属于流程隔离，不是操作系统安全边界。** 当前完全信任 Shell 仍可能读取工作区外路径。若需声称评分器对 Agent 不可见，必须在独立容器或 VM 中运行 Agent，将隐藏评分器保留在宿主外侧，并限制挂载与网络。没有此条件时，报告中需注明不可排除读取外部评分材料。

首版限制还包括：

- 人工构造、小代码量，缺少真实用户失败和真实开源历史任务。
- dev 与 holdout 家族隔离，但同家族内仍有相关性，且采用同类基础语言机制。
- 不覆盖完整 Web 前后端、数据库、依赖安装、复杂构建或大型仓库。
- 没有记忆生命周期、自动摘要、长时恢复、权限故障和网络扰动的效果任务。
- `file_contains`、`response_contains` 等规则只能证明字面条件；不得写成语义理解结论。
- 跨模块题以公开 API 和行为验收为主，不强制固定源码布局；架构可读性需要单独审查。

这些限制应随结果一起公开，下一版本优先添加真实使用中经脱敏且获得许可的失败案例。
